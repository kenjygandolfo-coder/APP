# Transactional macro-goal save via Postgres RPC (v1)

`saveMacroGoal` used to switch the active goal in two separate client round-trips — deactivate the current active row, then insert the new one — which is not atomic: if the insert failed after the deactivate committed, the user was left with no active goal. This change moves the whole switch into a single plpgsql function, `public.save_active_macro_goal` (migration 0002), that derives the owner from `auth.uid()`, deactivates the caller's active goals, inserts the new active row, and returns it, all inside one transaction. The data layer now makes one `client.rpc(...)` call passing only the goal fields (never `user_id`/`is_active`), the function is strictly typed in `database.types.ts` with no `any`, and the save test suite was rewritten to mock `rpc`. The partial unique index from 0001 stays as the backstop and 0001 is untouched.

Watch for: the data layer returns `data` directly as a non-null `MacroGoal` while the RPC error-path contract can hand back `data: null` with `error: null` — confirmed the typing asserts non-null, so a null-with-no-error response would propagate as `null` at runtime despite the `Promise<MacroGoal>` signature (possible). Function execute grants are not explicitly managed, so it inherits PostgREST's default exposure to the `anon` role; the `auth.uid() is null` guard makes that fail closed (possible).

**Verdict**: APPROVED

## High-level view

The atomicity fix is well-placed: a plpgsql function body runs inside the calling statement's transaction, so the deactivate and insert are genuinely all-or-nothing and the "no active goal" window is closed at the database, not patched in the client. The design chose `security invoker` over `definer`, which is the right call here — the function adds atomicity only, and leaving the existing per-command RLS policies in force (rather than bypassing them with definer rights) keeps `auth.uid() = user_id` as the authority on both the update and the insert. `search_path` is pinned to empty with every object fully qualified, closing the usual search-path-injection vector.

Ownership is never trusted from the client. The function reads `auth.uid()` server-side, raises on a null uid, and the data layer passes only the six goal columns — the tests now assert the args object carries no `user_id` or `is_active`. This closes the loop with the RLS model from 0001.

Error mapping stays non-leaky: the raw Postgrest error rides only on `Error.cause`, never interpolated into the message, and the rewritten test asserts the surfaced message contains none of the raw `message`/`details`/`hint` strings.

The one thing worth a second look is a type-vs-runtime gap: the hand-written `Returns` type drops the `null` the Supabase result union would carry, so `saveMacroGoal` returns `data` as a non-null `MacroGoal` even though a `{ data: null, error: null }` response would return `null` at runtime. Low severity — the SQL always returns a row or raises — but the signature and the possible runtime value are out of sync.

### Atomicity and rollback semantics of 0002

The function body — guard, `update ... set is_active = false where user_id = v_uid and is_active`, then `insert ... returning * into v_row` — executes inside the single transaction of the statement that invokes it. There is no nested `begin/commit` and no exception handler that would swallow a failure, so any error in the insert (including the partial unique index firing) aborts the whole function and rolls the deactivate back with it. That is exactly the property the two-round-trip client code could not provide: there is no committed intermediate state where the old goal is deactivated but the new one is absent.

The index `macro_goals_one_active_per_user` from 0001 remains the real guarantee of the single-active invariant. The function cooperates with it by deactivating before inserting, but if a bug ever left a second active row in play, the index raises a unique violation and the transaction rolls back rather than persisting two active goals. Keeping the index as the backstop rather than relying on the function's ordering is the correct layering.

### auth.uid() ownership and the invoker/definer choice

Ownership is derived from `auth.uid()` into `v_uid`, and the insert hard-codes `user_id = v_uid`; the client has no way to assert a different owner because the function signature exposes only the six goal parameters. A null uid raises `28000` before any write. This mirrors the 0001 RLS model where ownership is always `auth.uid()`.

`security invoker` is the right choice. The function adds atomicity, not privilege, so running with the caller's rights keeps the per-command policies (`macro_goals_update_own`, `macro_goals_insert_own`, both scoped to `auth.uid() = user_id`) in force on the update and insert inside the body. A `definer` function would have bypassed those policies and reintroduced the escalation risk the RLS layer exists to prevent. `set search_path = ''` with fully-qualified `public.*` and `auth.uid()` references closes search-path injection.

One operational note: migration 0002 does not manage execute privileges. In a Supabase project, a `public.*` function is exposed through PostgREST and callable by the `anon` role by default. Here that is not an exploit — the `auth.uid() is null` guard rejects an unauthenticated call, so it fails closed — but an explicit `revoke execute ... from public` plus `grant execute ... to authenticated` would make the exposure deliberate rather than inherited (possible).

### Data-layer call shape and non-leaky errors

```
client.rpc('save_active_macro_goal', {
  p_goal_type, p_tdee, p_calorie_target, p_protein_g, p_fat_g, p_carbs_g
})
```

The args object is built fresh from `input` field-by-field, so the caller's object is never mutated and no `user_id`/`is_active` leaks into the call — the "never sources ownership from the client" test asserts both the exact arg set and the absence of those two keys. `toClearError` attaches the raw Postgrest error only on `cause` and surfaces a fixed context string, so schema/policy/hint details do not reach the UI; the rewritten error test checks the message against the raw `message`, `details`, and `hint` values.

The success path returns `data` directly. The hand-written `Returns: ...['macro_goals']['Row']` makes `data` non-null on the typed result, which is why `return data` satisfies `Promise<MacroGoal>` under strict mode. That is accurate for this function (a composite-returning function yields a row or raises), but it collapses the `data: Row | null` union the Supabase result would otherwise carry, so a `{ data: null, error: null }` shape would type-check and return `null`. A `if (!data) throw toClearError(...)` or `return data ?? ...` would realign the signature with the runtime contract; low severity because the SQL cannot actually produce that shape.

### Strict typing of the Function

`p_goal_type` is typed `GoalType`, matching the SQL `public.goal_type` enum parameter, so a bad enum value is rejected at both the TS boundary and the database. The remaining `p_*` args and the Row `Returns` are mapped with no `any`.

### Test coverage

The save suite now exercises: one-call-and-returns-the-row (asserting `rpc` called exactly once with the derived args), the ownership-isolation assertion (no `user_id`/`is_active` in args), input non-mutation, and non-leaky error mapping. The getter suite and its leak assertions are unchanged. Dropping the old separate "deactivate fails" / "insert fails" cases is correct — those failure modes no longer exist as distinct client steps; a single `rpc` error now covers both.

Not tested: the actual transactional rollback and the partial-unique-index backstop. These live entirely in SQL and there is no sandbox Postgres to execute 0002 against, so the all-or-nothing behavior, the `28000` null-uid raise, and the unique-violation-triggered rollback are verified by static reading only (confirmed, environment-limited). The intentionally-unchanged `useSaveMacroGoal.test.tsx` and `saveGoalWiring.integration.test.tsx` mock the data layer, so they remain valid without edits.
