# Supabase data layer for macros-web — schema, RLS, typed client, and query hooks (v1)

This change adds the Module 3 data layer entirely under `apps/macros-web/`: a single SQL migration defining four tables (`profiles`, `macro_goals`, `weight_logs`, `food_logs`) with an `updated_at` trigger and per-command RLS scoped to `auth.uid()`; a hand-written strict `Database` type; a secret-safe env reader plus a lazily-memoized typed Supabase client; a pure async data-access pair for the active macro goal; and TanStack Query read/mutate hooks wired at the app root. The approach keeps authorization server-side in RLS, keeps the client functions pure with injected clients, and maps Postgrest failures to non-leaking errors. Strict TS holds (no `any`), no `console` calls, and immutability is respected throughout.

Watch for: the `saveMacroGoal` deactivate-then-insert sequence is two separate non-transactional round trips, so a failed insert after a successful deactivate leaves the user with zero active goals (confirmed). Everything else is sound.

**Verdict**: APPROVED

## High-level view

The schema puts the ownership boundary in the database. Every table enables RLS and defines four explicit per-command policies keyed on `auth.uid()` (`id` for `profiles`, `user_id` for the rest), with `WITH CHECK` on insert and `USING`+`WITH CHECK` on update so a row can neither be created for nor reassigned to another user. All foreign keys reference `auth.users` with `ON DELETE CASCADE`, and the single-active-goal invariant is enforced by a partial unique index rather than trusted to the client.

The client layer never reads secrets from anywhere but `import.meta.env` VITE vars, fails with a clear message naming each missing variable, and only ever handles the public anon key. The data functions take the client as a parameter (pure, injectable), return mapped rows or `null`, and translate Postgrest errors into a stable `macro-goals: <context>` message that keeps the raw message/details/hint off the surfaced string (attached only as `cause`).

The two hooks use `useQuery`/`useMutation` with no `useEffect` for fetching; the read hook stays idle until a `userId` exists, and the mutation invalidates the exact active-goal key through a shared key factory so a save reliably refreshes the read.

The one behavioral gap is in the save strategy: deactivate and insert are independent network calls with no transaction, so a mid-sequence failure can leave the user with no active goal.

### RLS keeps ownership in the database, not the client

The migration enables RLS on all four tables and defines a full four-command policy set per table (select/insert/update/delete), each scoped to `authenticated` and gated on the owner key — `auth.uid() = id` for `profiles`, `auth.uid() = user_id` for the three log/goal tables. Insert policies gate the incoming row with `WITH CHECK`, and update policies pair `USING` (which existing rows are visible to update) with `WITH CHECK` (what the row may become), which closes the reassignment hole where a user flips `user_id` to someone else. Static reading confirms the counts: 4× `enable row level security`, 16 `create policy`, 8 `with check`, 4 `on delete cascade`. No live DB was available, so this is a static validation of policy structure, not an executed test.

The `goal_type` enum uses unaccented ASCII (`deficit`/`mantenimiento`/`volumen`) and the file documents that the accented UI label lives in the copy layer — the TypeScript `GoalType` union matches exactly, so the DB enum and the client type cannot drift silently.

### Single-active-goal invariant and the non-atomic save

The invariant is enforced structurally by `create unique index ... macro_goals (user_id) where is_active`, so even a buggy client cannot produce two active goals. The data layer's `saveMacroGoal` cooperates with that index by first setting `is_active = false` on the user's active rows, then inserting the new row with `is_active = true`.

The concern is that these are two independent client-issued statements, not one transaction:

```
update macro_goals set is_active=false where user_id=? and is_active   -- call 1
insert into macro_goals (...) values (...) returning *                 -- call 2
```

If call 1 succeeds and call 2 fails (network drop, check-constraint violation, RLS rejection), the previously active goal is already deactivated and nothing replaces it — the user ends up with no active goal, and `getActiveMacroGoal` will subsequently return `null`. There is no compensating re-activation. For a goal the user just edited this is a recoverable annoyance rather than data loss, but it is a real failure mode worth closing by moving both writes into a single Postgres function/RPC (or a transaction) so the deactivate rolls back when the insert fails.

### Env reader and client isolate the secret boundary correctly

`readSupabaseEnv` reads only `VITE_SUPABASE_URL` and `VITE_SUPABASE_ANON_KEY`, trims them, and throws an error that names every missing variable and points at `.env.example` without echoing any value that *was* present. The returned object is frozen. `getSupabaseClient` builds the client lazily and memoizes it, so the missing-env error only fires when Supabase is actually used, and tests inject their own client instead of touching env. `.env.example` and `vite-env.d.ts` document the anon key as public-by-design and warn against committing a `service_role` key; `.gitignore` was updated in the deps commit to ignore `.env`/`.env.*`. The anon key is the only credential in play.

### Error mapping does not leak Postgrest internals

`toClearError` returns `new Error('macro-goals: ' + context, { cause: error })` and never interpolates the Postgrest `message`/`details`/`hint` into the surfaced string. The data-layer test asserts this directly by seeding a Postgrest error carrying `super-secret-detail`, `leak-hint`, and `permission denied` and verifying none of them appear in the thrown message across the getter, the deactivate failure, and the insert failure — a meaningful leak test, not a static assertion.

### Hooks: no useEffect fetching, correct invalidation

`useMacroGoal` is a `useQuery` disabled via `enabled: Boolean(userId)`, so a `null`/`undefined` user stays idle rather than firing a request with a bogus id; the test confirms `fetchStatus === 'idle'` and that the data function is never called. `useSaveMacroGoal` is a `useMutation` whose `onSuccess` invalidates `macroGoalKeys.active(userId)`. Both hooks and the read share the same frozen key factory, so the invalidation tuple provably matches the query tuple. The mutation test drives a real `QueryClient`, holds the promise open to observe `isPending`, resolves it to observe `isSuccess` + `data`, and spies on `invalidateQueries` to confirm it fires with the exact key on success and does *not* fire on rejection — covering the loading/error/pending surface the requirement called out.

### Strict typing and immutability

`SaveMacroGoalInput` is derived as `Omit<Insert, 'id'|'created_at'|'updated_at'>` so callers can't pass server-managed columns. `saveMacroGoal` builds `{ ...input, is_active: true }` rather than mutating the argument, and a dedicated test asserts the input object is unchanged and never gains an `is_active` property. No `any` and no `console` appear anywhere in the new `src/lib`, `src/data`, `src/features/macro-goals`, or `src/app` files.

### Tests exercise behavior; coverage is self-contained

The new suites run standalone (`npm run test -- --run src/features/macro-goals src/lib src/app`) and all 24 of their cases pass. They mock the Supabase chain at the method level and assert real behavior — the deactivate-then-insert ordering and payload, the `null`-on-no-row path, env trimming/missing-var naming, lazy memoization of the client, and the hook state transitions. The only failing file in that run is the pre-existing `src/App.test.tsx`, which fails solely because the `@energy` alias is absent on this branch; it is unrelated to this change and out of scope.

Not tested: the SQL/RLS itself (no live database in the sandbox — validated statically only), and the non-atomic-save partial-failure path described above is not simulated.
