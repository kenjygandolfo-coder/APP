# Real Supabase Auth login wiring (v1)

The auth module's submit stub is replaced with real Supabase Auth calls. A pure data layer (`auth.data.ts`) wraps `signInWithPassword` / `signUp` / `signOut` / `getSession` / `getUser` over an injected typed client; a `SessionProvider` seeds the session on mount and tracks it via `onAuthStateChange`; `useSession` / `useCurrentUserId` expose a plain `userId` to the data hooks. The forms now default to the real handlers while keeping `onSubmit` injectable for tests, and the dev placeholder token (`session-${Date.now()}`) plus the `useAuthStorage` dependency were removed so supabase-js is the single owner of session persistence. The approach is clean, well-decoupled, and the security posture (no password logging, non-leaky error mapping, `confirmPassword` dropped before the provider) is handled deliberately.

Watch for: (1) `useSaveMacroGoal(userId)` is called in `App.tsx` but its mutation handle is never wired into the wizard, so a real goal is never persisted — the "save" half of the stated goal is only half-connected (likely). (2) `SessionProvider` runs two independent `setState` paths (the async `getCurrentSession` seed and the sync `onAuthStateChange` subscription) with no ordering guard, so a slow seed can clobber a newer auth event (possible). (3) Sign-up with email confirmation returns a `null` session yet the form still flips to the success state, which may mislead the user (likely).

**Verdict**: NEEDS_CHANGES

## High-level view

Every data-layer call takes the `SupabaseClient<Database>` as a parameter rather than a singleton, so the unit tests run without env vars. Provider errors are collapsed into a fixed `auth: <context>` message with the raw error tucked into `cause`, never interpolated into the surfaced message — asserted by the raw-leak test.

Session state has one owner: `SessionProvider` derives `{ session, user, userId, status }` through `toSessionState` and the forms discard the session sign-in returns because the `onAuthStateChange` subscription is the source of truth. The wrinkle is bootstrap ordering — the explicit `getCurrentSession` seed and the subscription both write state, and nothing enforces that a late-resolving seed loses to an auth event that already arrived.

The placeholder token and `useAuthStorage` dependency are gone, which removes the double-storage risk the previous stub carried; `confirmPassword` is dropped in `makeRegisterSubmit` and never reaches `signUp`.

The gap is the data-write seam. The user's goal is that `useMacroGoal` *and* `useSaveMacroGoal` receive a real `userId`. `useMacroGoal` does, through `SessionPanel`. But `useSaveMacroGoal(userId)` in `App.tsx` returns a mutation that is never invoked anywhere — the wizard has no reference to it — so the authenticated user can read a goal but the save path is a dead end.

1. **Save mutation never invoked** — `useSaveMacroGoal(userId)` in `App.tsx` discards its return and the wizard never calls `mutate`, so no goal is ever persisted against the real user. Wire the mutation into the wizard's save action (or document that persistence is a later module).

3. **Sign-up success on null session** — `signUpWithPassword` can resolve a `null` session (email confirmation) yet the form flips to `submitted`/success. Branch on the returned session so the confirmation-pending case shows a "check your email" state instead of implying an active session.
4. **act() warning from SessionProvider** — the async seed updates state outside `act` in tests, emitting a React warning. Have tests await the settled state (or wrap the trigger) so the suite stays clean.

### Session ownership and the bootstrap race

`SessionProvider` does two things on mount: it calls `getCurrentSession(client)` and, independently, subscribes to `onAuthStateChange`. Both resolve into `setState(toSessionState(...))`. The `active` flag correctly prevents a state write after unmount, but it does not order the two writers. supabase-js's `onAuthStateChange` emits an `INITIAL_SESSION` event shortly after subscription, which already carries the bootstrap session — so the explicit `getCurrentSession` seed is largely redundant and is the source of the race: if an auth event lands before the seed promise resolves, the later-resolving seed will overwrite the newer state with the bootstrap value.

```
mount
 ├─ getCurrentSession() ──(async)──────────────▶ setState(seed)   ← can land LAST
 └─ onAuthStateChange(cb)
        └─ cb(INITIAL_SESSION / SIGNED_IN) ────▶ setState(event)  ← newer, but earlier
```

In practice the seed usually wins the race the "right" way because the subscription's first emit is also async, but nothing guarantees it. Relying on the subscription alone (and letting `status` stay `loading` until the first emit) would remove the second writer entirely. If the explicit seed is kept for a faster first paint, it should only apply while `status === 'loading'` so it can never clobber a real event.

### Sign-up with email confirmation

`signUpWithPassword` is documented to return `Session | null` because confirmation-required projects return no session until the email link is clicked. `makeRegisterSubmit` awaits it and resolves `void`; `useAuthSubmit` then sets `submitted = true` and fires `onSuccess` regardless of whether a session materialized. So a user who registers against a confirmation-enabled project sees the success state even though they are not signed in and `onAuthStateChange` will not fire. The friendly-error path is unaffected (a thrown error still shows the Spanish message), but the success path conflates "account created, check your email" with "signed in." Branching on the returned session — surfacing it from the handler rather than discarding it — would let Registro show the correct pending-confirmation copy.

### The save seam is not connected

`SessionPanel` passes the live `userId` into `useMacroGoal`, so the read side lights up with a real user — the integration test confirms the query flips from `idle` to `fetching` once a `userId` exists. The write side does not. `App.tsx` calls `useSaveMacroGoal(userId)` purely for its side effect of instantiating the mutation, but the returned `mutate` / `mutateAsync` is discarded, and a grep across the wizard finds no reference to `useSaveMacroGoal`, `mutate`, or any save handler. The authenticated user therefore cannot actually persist a goal through this change. The user instruction names both hooks as needing a real `userId`; `useMacroGoal` is satisfied, `useSaveMacroGoal` is instantiated but inert. Either wire the mutation into the wizard's save action or make the intent explicit that persistence lands in a later module — as written, the call in `App.tsx` reads as dead code.

### Test coverage

Covered: the data layer has success-and-error cases for all five functions with the raw-leak assertion; `useSession` covers seeding, the flip to anonymous, single-unsubscribe-on-unmount, and the outside-provider throw; the integration test drives a login through the real form and asserts the macro-goal query flips to enabled; `SessionPanel` covers the authenticated/anonymous renders and the sign-out click.

Not tested: the sign-up null-session path (no test asserts what the form does when `signUp` returns no session); the bootstrap race (no test fires an auth event before the seed resolves); and the inert `useSaveMacroGoal` wiring (nothing asserts a save actually persists). The `SessionProvider` async seed also triggers a React `act()` warning in the suite — tests pass but update state outside `act`, which should be tidied so a real future warning isn't lost in the noise.
