# Food-logs daily dashboard timezone + wiring fixes (v2)

Second pass over the food-logs module after the fix commit `a5e00bc` addressed the two blocking findings from v1. The write/read date mismatch is resolved by a new shared pure `today.ts` (`localToday(now = new Date())`) consumed by both the dashboard (query date) and the form (insert stamp), and the previously untested `App.tsx` diary wiring now has signed-in and signed-out coverage. Both v1 issues are genuinely closed, no regression was introduced, and the third (informational) item was knowingly kept and justified.

Watch for: nothing blocking. One minor observation (confirmed, non-blocking): `localToday()` is evaluated at the moment of submit inside the form's `onSubmit`, so a log entered just after local midnight is stamped with the new day while the dashboard — mounted earlier — still queries the previous day's key until it re-renders; this is a far narrower window than the v1 UTC-wide gap and is acceptable.

**Verdict**: APPROVED

## High-level view

The v1 timezone hole is closed by construction. A single pure module, `today.ts`, is now the only source of the `yyyy-mm-dd` day string. The dashboard imports it for its query date and the form imports it to stamp `logged_on` on the insert payload, so the row lands on exactly the date the dashboard subscribes to and the `useAddFoodLog` invalidation (keyed on `saved.logged_on`) hits the watched key. The data layer needed no change: `AddFoodLogInput` already permits `logged_on` (it is optional on the DB `Insert` type, not omitted), and `addFoodLog`'s `...input` spread passes a caller-supplied `logged_on` through without clobbering it.

The v1 coverage gap is closed. `App.test.tsx` now parametrizes its mock client with an `initialSession` and adds a signed-in case (selecting the `Diario` nav renders both the dashboard and form headings, and asserts the signed-out prompt is absent) and a signed-out case (selecting `Diario` renders the `DIARIO_SIGNED_OUT` prompt and neither heading). The nav label and prompt string literals in the test match `App.tsx` exactly, and the original three tests — including the deliberate `@energy` import and `calculateTdee` assertion — are preserved verbatim.

The third v1 item (data-layer `unit` default `'serving'` vs DB `'g'`) was informational and was intentionally kept, documented in the task findings: the manual form captures per-serving totals and `addFoodLog` is the only insert path, so the data-layer default is load-bearing by design.

Full suite is green and clean: 204/204 across 36 files with the `@energy` domain materialized, the food-logs suite is self-contained at 46/46, typecheck passes once `@energy` resolves, and lint is clean.

### Issue #1 (timezone write/read mismatch) — resolved by a shared day source

The fix extracts the exact `localToday` logic that lived privately in `DailyDashboard.tsx` into `food-logs/today.ts` and makes it injectable (`now: Date = new Date()`) for deterministic testing. The dashboard deleted its private copy and imports the shared one for its query date; `ManualFoodForm` imports the same helper and sets `logged_on: localToday()` on the `AddFoodLogInput` it hands to `mutate`:

```ts
const input: AddFoodLogInput = {
  user_id: userId,
  name: values.name,
  calories: values.calories,
  protein_g: values.protein_g,
  fat_g: values.fat_g,
  carbs_g: values.carbs_g,
  logged_on: localToday(),
};
```

Because both sides derive the date from one pure function, the row is written under the same local calendar day the dashboard subscribes to. The chain that was broken in v1 now closes: the write stamps day `D`, `useAddFoodLog` invalidates `foodLogKeys.daily(userId, saved.logged_on)` = `daily(userId, D)`, and the dashboard is watching `daily(userId, D)`. The late-night off-UTC case that silently dropped the item is gone.

The data layer required no edit, and the briefing's two checks hold: `AddFoodLogInput` is `Omit<FoodLogInsert, 'id'|'created_at'|'updated_at'|'quantity'> & { quantity?: number }`, and `logged_on` is optional on the DB `Insert` type, so it is carried through rather than omitted — a caller may now legitimately supply it. And `addFoodLog` builds `{ ...input, quantity: input.quantity ?? 1, unit: input.unit ?? 'serving' }`, so a provided `logged_on` flows through the spread untouched; only `quantity`/`unit` get defaults, and even those defer to a caller-provided value. No clobber.

Coverage for the fix is real, not cosmetic. `today.test.ts` pins the behavior that matters: a `2026-03-07 23:30` local time yields `2026-03-07` (not a UTC-shifted `03-08`), single-digit months/days zero-pad, a late-night `2026-12-31 22:15` stays on `12-31`, and the no-arg path matches the explicit-`new Date()` path. The new `ManualFoodForm` test asserts the `mutate` payload's `logged_on` equals `localToday()` and matches `/^\d{4}-\d{2}-\d{2}$/`, and the pre-existing payload-equality test was updated to include `logged_on` — so the write-side stamp is locked in by assertion.

One residual, narrow and non-blocking: `localToday()` is read at submit time, while the dashboard's query key was fixed when it mounted. A session that crosses local midnight between dashboard mount and form submit would stamp the new day while the dashboard still watches the old key, so the invalidation misses until the dashboard re-renders. This is the inherent "render-time snapshot of now" limitation, orders of magnitude narrower than the v1 UTC-offset gap that hit every off-UTC user every day, and not worth gating on.

### Issue #2 (untested App.tsx diary wiring) — resolved with signed-in and signed-out cases

`App.test.tsx` now mocks `./lib/supabaseClient`, `macroGoals.data`, and `foodLogs.data` so the TanStack hooks under the diary resolve deterministically, and `makeMockClient(initialSession)` lets a test boot the app signed-in or anonymous. The signed-in case waits for the authenticated state to settle (the "cerrar sesión" button), clicks the `Diario` nav, and asserts both `FOOD_COPY.dashboard.title` and `FOOD_COPY.form.title` headings render while `DIARIO_SIGNED_OUT` is absent — exercising the `userId`-gated branch of `renderDiario`. The signed-out case clicks `Diario` and asserts the prompt shows and neither heading renders — the fallback branch. The literals the test hardcodes (`DIARIO_LABEL = 'Diario'`, `DIARIO_SIGNED_OUT = 'Inicia sesión para ver tu diario de hoy.'`) match `App.tsx` line-for-line, so the assertions are wired to the real UI, and `renderDiario`'s `userId ? (dashboard+form) : (prompt)` gate is now covered on both arms.

The original three App tests are intact, including the `@energy`-alias import and the `calculateTdee` assertion that the briefing flagged as deliberate.

### No regression and the kept decision

Running from the app package (`apps/macros-web`, where the jsdom Vitest config lives) the food-logs suite is 46/46 and the full suite is 204/204 across 36 files with the `@energy` domain temporarily materialized — up from v1's 197, matching the +7 the task record claims (4 `today` + 1 `ManualFoodForm` + 2 `App`). No action needed.
