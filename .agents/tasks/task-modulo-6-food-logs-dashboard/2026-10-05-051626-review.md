# Food-logs daily dashboard + manual entry module (v1)

Adds the real-time macro "diary" to the web module: a pure data layer over `food_logs` (read a user's logs for a date, insert a log), two TanStack Query hooks (`useDailyFoodLogs`, `useAddFoodLog`), a React-free `summarizeDailyMacros` math module, a `ManualFoodForm` (react-hook-form + zod) that clears on save, a `DailyDashboard` composing the active goal and today's logs, and a `Diario` nav view wired into `App.tsx` behind an authenticated `userId`. The feature faithfully mirrors the sibling `macro-goals` pattern — frozen query-key factory, non-leaky `toClearError`, enabled-gated `useQuery`, invalidate-on-success `useMutation` — and honors every stated hard constraint: no AI/external search, no `useEffect` for fetching, zero `any`, no `console.*`, reused FormCard/TextField/PrimaryButton, immutable reduce, zod validation, and the exact over-budget UX (bar clamped at 100%, real negative remaining shown in the pink accent). All 41 new tests pass.

Watch for: a **timezone mismatch between where an inserted log lands and what the dashboard queries** (confirmed) — the dashboard subscribes to the browser-local date while inserts take the DB `current_date` (UTC) default, so for users off UTC a freshly logged item can silently fail to appear and the real-time refresh breaks. Also the new `Diario` nav/signed-out wiring in `App.tsx` has **no test coverage** (confirmed), contrary to the plan's own instruction to update `App.test.tsx` when the nav changes.

**Verdict**: NEEDS_CHANGES

## High-level view

The data and hook layer is a clean clone of `macro-goals`: pure async functions take the Supabase client as a parameter, errors are wrapped so Postgrest internals live only in `cause`, the query-key factory is frozen and keyed by both `userId` and `date`, and the mutation invalidates exactly `foodLogKeys.daily(userId, saved.logged_on)` on success. Per-date invalidation precision is real — the key tuple carries the date, so adding to one day never refetches another.

The real-time contract has a timezone hole. The dashboard computes "today" from local date parts (`localToday()`) and queries that string; the insert omits `logged_on`, so Postgres fills it with `current_date` evaluated in the DB timezone (UTC per the migration default). When the local date and UTC date disagree, the row is written under one `logged_on` while the dashboard is subscribed to another, so the invalidation fires against a key the dashboard isn't watching and the just-added food never shows until a manual reload lands on the matching date. This defeats the stated "dashboard updates in real time" goal for a slice of users.

The summarize math is correct and genuinely pure: a frozen zero seed, a non-mutating reduce, `remaining` left signed (negatives preserved), `percent` clamped to `[0,100]`, and a `null` goal mapped to zero targets so there is no `NaN` or divide-by-zero. The dashboard renders loading → error → no-goal → summary in that order and never surfaces a raw error. Over-budget behavior matches the spec exactly.

The form validates name/calories/protein/fat/carbs with zod (calories coerced and rounded to a non-negative integer, macros non-negative decimals), submits through `useAddFoodLog`, and resets on the mutation's `onSuccess`. The `quantity=1`/`unit='serving'` defaults are applied immutably in the data layer and are the documented decision.

The `App.tsx` wiring gates the diary behind a real `userId` and falls back to a friendly prompt when signed out, but that branch and the new nav button are untested.

<summary>Details</summary>

### Per-date invalidation is precise, and the read/write key agree by construction

`foodLogKeys.daily` is a frozen factory producing `['food-logs','daily',userId,date] as const`, and both the read hook and the mutation consume it, so the tuple can't drift between subscribe and invalidate. `useAddFoodLog` invalidates `foodLogKeys.daily(userId, saved.logged_on)` — keyed off the persisted row's own date, so an insert for one day leaves other cached days untouched. The invalidation-precision requirement is met; the test spies on `invalidateQueries` and asserts the exact key, and separately asserts no invalidation on rejection.

### Local-vs-UTC date splits the write from the read

The precision above is only useful if the date the dashboard subscribes to is the date the row is written under. It isn't, in general. `DailyDashboard` builds the query date from local parts:

```ts
function localToday(): string {
  const now = new Date();
  const year = now.getFullYear();
  const month = String(now.getMonth() + 1).padStart(2, '0');
  const day = String(now.getDate()).padStart(2, '0');
  return `${year}-${month}-${day}`; // browser-local calendar date
}
```

`addFoodLog` builds its insert from `AddFoodLogInput`, which omits `logged_on`:

```ts
const insertRow = { ...input, quantity: input.quantity ?? 1, unit: input.unit ?? 'serving' };
```

and the migration defines the column as `logged_on date not null default current_date`. `current_date` is the DB session date (UTC by default on Supabase). So a user at 21:00 US-Pacific logs food on their local "today" `D`, the row is written with `logged_on = D+1` (UTC), the mutation invalidates `daily(user, D+1)`, and the dashboard is watching `daily(user, D)`. The new item is invisible until the clocks line up. The comment on `localToday()` explicitly reasons about avoiding `toISOString()` UTC drift on the read side — but the write side reintroduces exactly that drift because it never sends a date. The fix is to make the insert carry the same local date the dashboard uses: add `logged_on` to `AddFoodLogInput`, set it from `localToday()` (or a shared helper) in `ManualFoodForm`/`DailyDashboard`, and the existing invalidation keyed on `saved.logged_on` then matches the subscribed key.

### summarizeDailyMacros: pure, signed remaining, clamped percent, null-goal safe

```ts
function percentOf(consumed: number, target: number): number {
  return target > 0 ? clamp((consumed / target) * 100, 0, 100) : 0;
}
```

A `null` goal maps to the frozen `ZERO_TOTALS`, so `percentOf` short-circuits to `0` (no divide-by-zero, no `NaN`) and `remaining` becomes the negated consumed — "negatives not hidden" holds even with no goal. `remaining` is never clamped; `percent` always is. The reduce seeds from the frozen zero object and returns fresh objects each step, so the accumulator and seed are never mutated. The six summarize tests cover empty/partial/at-goal/over-goal/no-goal.

### Over-budget UX matches the spec in both the calorie headline and the bars

`MacroProgressBar` receives a pre-clamped `percent` for the fill width and separately renders `Math.round(remaining)` with `text-pink` when `remaining < 0`, so the track never exceeds 100% while the real negative number stays visible. The dashboard mirrors this for the calorie headline (`text-pink` + `overBudget` copy when `remaining.calories < 0`). The dashboard test asserts protein remaining `-50g` in `text-pink`, fill width `100%`, `aria-valuenow` `100`, and the `-500` calorie headline simultaneously — the exact decision the user specified.

### Form validation, coercion, and clear-on-save

Calories coerce then `transform(Math.round)` so `"120.6"` saves as `121`; macros coerce to non-negative decimals. `onSuccess` calls `reset(foodLogDefaults)`, and the integration test confirms every field returns to empty/`null` after a save, that invalid input blocks `mutate`, and that failure shows friendly copy (asserting the raw error text is absent). The one `as unknown as DefaultValues<FoodFormValues>` cast is the string-input-over-numeric-schema seam the macros-wizard sibling already uses — worth confirming it survived the zero-`any` constraint, and it does (it is a cast, not an `any`).

### Non-leaky errors confirmed by assertion

`toClearError` returns `new Error(\`food-logs: ${context}\`, { cause: error })` — the raw Postgrest `message`/`details`/`hint` go only to `cause`. The data tests feed an error carrying `super-secret-detail`/`leak-hint`/`permission denied` and assert none of those strings appear in the surfaced message while `cause` still holds the raw object. Both the dashboard and form error-state tests also assert the rendered alert never matches `/postgrest|supabase|Error:/i`.
