# Macros Calculator Wizard — Vite/React web module (v1)

A new Vite + React 18 + TypeScript (strict) + Tailwind v3 web module at `apps/macros-web` implements the four-step macros wizard. Rather than reimplement the energy math, it reuses the repo's portable energy domain (`src/features/energy/domain`) through an `@energy` path alias and layers a thin, pure `calculateMacros` on top that turns a maintenance TDEE into a protein/fat/carbs split. The UI is a single react-hook-form instance spanning all four steps with per-step `trigger()` gating, so "Corregir datos" returns to step 1 with every value intact, and "Guardar mis metas" flips a React state flag that renders a success banner — no `console.log`, no backend, no persistence. The cozy palette, fonts, radius, and card translucency live as Tailwind theme tokens, and the component classes reference those tokens rather than scattering hex.

Watch for: a dead `COPY.app` title/subtitle block that is defined but never rendered, so the app ships without the title the brief asked for (confirmed, minor); a misleading comment in `TextField` claiming "pink-adjacent" error text when the error color is actually sage green (confirmed, cosmetic); and a defensive calculation-error path in the results memo that per-step gating makes effectively unreachable (confirmed, not a defect). None of these block shipping.

**Verdict**: APPROVED

## High-level view

The architecture decision — a dedicated DOM module instead of forcing Tailwind/`<select>` into the Expo React Native root — is sound and clearly justified in the plan: Tailwind and native DOM form controls do not render under React Native, and the user explicitly asked for React + Tailwind. The module reuses rather than forks the energy domain via `@energy`, aliased consistently in `vite.config.ts`, `vitest.config.ts`, and `tsconfig.json`, with an `App.test.tsx` case that exists specifically to prove the alias resolves the shared code under Vitest.

The macro math is a genuinely pure function: it validates its input through the reused zod schema, derives `calorieTarget = round(TDEE)`, computes each macro's grams from a frozen 30/25/45 split and Atwater factors (4/4/9), recomputes kcal from the rounded grams so the two never drift, and returns a deeply frozen result. Invalid input throws `CalculationInputError` carrying field/message pairs with no raw values echoed.

Cross-step state is one RHF form with a zod resolver; `z.coerce.number` bridges the string-valued DOM inputs to the numeric `TdeeInput`. `STEP_FIELDS` drives per-step validation so a step cannot be skipped past empty or invalid fields, and because the form instance is never reset, "Corregir datos" preserves data by construction.

The test suite is behavioral, not trivial: the domain suite hand-computes reference grams and checks immutability, no-leak error handling, and every activity level for both sexes; the integration suite drives the real DOM through all four steps and asserts the rendered numbers match `calculateMacros`, that gating blocks advancement, that edit preserves values, and that save produces a banner without touching `console`. E2E covers the happy path and the data-preservation-on-edit flow against the built app.

All source files stay well under the 800-line limit (largest is `MacrosWizard.tsx` at 118 lines) with no function near 50 lines, split by concern. The known gaps are cosmetic: the app-level title/subtitle copy is defined but never mounted, and an error-text comment misdescribes its own color.

### Separate web module as an architecture decision

The brief asked for React + Tailwind with DOM `<select>`/`<input>` controls; the repository root is an Expo/React Native app where Tailwind utility classes and native DOM form elements do not render. Standing up `apps/macros-web` as a Vite SPA is the right call, and it avoids the trap of reimplementing the energy formulas: `src/domain/index.ts` re-exports `calculateTdee`, `tdeeInputSchema`, `CalculationInputError`, `ACTIVITY_LEVELS`, `SEXES`, and `INPUT_LIMITS` straight from `@energy`. The alias is defined identically in all three toolchains (Vite build, Vitest, and tsc path mapping), and `App.test.tsx` asserts `calculateTdee(...)` returns `multiplier === 1.55` for a moderate male — a real cross-module resolution check, not a smoke import.

### The macro math stays pure and internally consistent

```
calorieTarget = round(TDEE)                         // TDEE from reused energy domain
grams(macro)  = round(calorieTarget * split / kcalPerGram)
kcal(macro)   = grams(macro) * kcalPerGram           // recomputed from rounded grams
```

Recomputing kcal from the already-rounded grams (rather than from the raw fractional calories) is the detail that keeps grams and kcal from telling two different stories; the suite pins this with `kcal === grams * KCAL_PER_GRAM[macro]` and separately bounds the reconstruction error (`|Σ macro kcal − calorieTarget| ≤ 9`) to acknowledge per-macro rounding slack. `MACRO_SPLIT` and `KCAL_PER_GRAM` are frozen and asserted to sum to 1.0; the result object and each breakdown are frozen, and a test confirms a frozen input is not mutated. This satisfies the immutability constraint without relying on convention.

Validation routes through the reused `tdeeInputSchema`, and the error path maps zod issues to `{ field, message }` without including the offending value. The suite explicitly feeds `weightKg: -987654` and asserts that number appears in neither the message nor the serialized issues — a direct check against sensitive-value leakage.

### Single form, real gating, lossless edit

`MacrosWizard` holds one `useForm` instance shared via `FormProvider`; steps read it through `useFormContext`. `handleNext` runs `trigger(STEP_FIELDS[currentStep])` and only advances when the current step's fields validate, so empty or invalid entries can't be skipped past. Because the form is never reset, `handleEdit` just clears the saved flag and sets `currentStep` back to 0 — data persistence is structural, not a copy-back. The integration test proves it end to end: complete the wizard as a male, click "Corregir datos," and assert age/gender on step 1 and weight/height on step 2 still hold their values. The `defaultValues` use empty strings to keep inputs controlled from first render while the schema still enforces presence (empty coerces to 0, which fails `positive()` — a case the suite asserts rather than assumes).

The results value is derived in a `useMemo` keyed on `currentStep`: on reaching step 4 it parses `getValues()` through the wizard schema and calls `calculateMacros`. On failure it returns `null` and the UI shows a `role="alert"` calculation-error message. Given the gating already validated all fields, this failure branch is practically unreachable in normal flow — fine as defense-in-depth, but it is not exercised by a test and shouldn't be mistaken for covered behavior.

### Save is state-driven, not logged

The brief offered "a console.log or a visual success state"; the implementation chose the state path. "Guardar mis metas" calls `onSave` → `setSaved(true)`, which renders a `role="status"` banner. The ESLint `no-console` rule is enforced and a grep across `src` and `e2e` finds no `console.*`. The integration test spies on `console.log`, triggers save, waits for the status banner, and asserts the spy was never called — so a regression that reintroduced logging would fail the suite, not pass it silently.

### Palette as tokens, fonts loaded

`tailwind.config.ts` encodes cream/sage/pink/ink/muted, the translucent `card` and `cardBorder`, the `card` 16px radius, and the Montserrat/Playfair font stacks; components reference `bg-sage`, `border-pink`, `rounded-card`, `font-serif`, etc., with the one unavoidable raw rgba living in `index.css` for the subtle sage dot-pattern background. Buttons carry `transition-transform duration-150 hover:-translate-y-0.5` and the hover lift; inputs/selects use `focus:border-sage`. Google Fonts are preconnected and loaded in `index.html`. The `fields.test.tsx` harness asserts the sage focus class, the pink secondary border, and the hover-lift class are actually present on the rendered elements — style assertions that would catch a token being dropped.

One mismatch: `TextField`'s doc comment says error text renders "in the pink-adjacent accent for readability," but the class is `text-sage`. The green is a defensible choice (the brief reserves pink for secondary details), so the fix is to the comment, not necessarily the color.
