# Auth module: Login + Registro with platform-adaptive token storage (v1)

Module 3 adds a Login/Registro flow to the `apps/macros-web` DOM module, reusing the Enchanted/Cozy design tokens and primitives from Module 2. The two forms are driven by react-hook-form + zodResolver with Spanish field errors and a cross-field password-match refinement on Registro. The submit path is backend-agnostic: an injectable `onSubmit` is ready for the future API/Supabase call, and in its absence a default handler logs only a redacted projection (`{ email, passwordLength }`) through an injectable logger before persisting a dev placeholder token. Token persistence sits behind a `TokenStorage` interface with two real implementations — `localStorage` for web and `expo-secure-store` (lazy dynamic import) for native — selected at runtime.

The user prompt is internally contradictory (React Native Expo *and* literal Tailwind classes *and* expo-secure-store *and* localStorage). The chosen resolution — build the literal-Tailwind UI in the web module and honor the storage decision as a dual-implementation abstraction — is the same honest resolution accepted for Module 2, and the native branch is genuinely implemented rather than hand-waved. The console.log-vs-no-console tension is resolved by routing the "log of validated data" through a redaction seam so the raw password is structurally unable to reach any sink.

Watch for: nothing blocking. The native expo-secure-store branch is exercised only via a mocked virtual module, never against a real device keystore (confirmed, inherent to a web module and acceptable); `App.tsx` view-switch branches are largely uncovered (confirmed, low risk); the localStorage XSS trade-off is documented but remains a real web-platform exposure the future API wiring must keep in mind (confirmed).

**Verdict**: APPROVED

## High-level view

A single `TokenStorage` interface backs both a `localStorage` web impl and an `expo-secure-store` native impl, selected at runtime by `createTokenStorage()`. The native impl defers its dependency through a runtime-computed dynamic import with `/* @vite-ignore */`, so the web build never resolves a package that isn't a web dependency — the detail that makes the dual-impl claim real rather than cosmetic, exercised only through a virtual mock.

The redaction seam is the second load-bearing decision: the logger type only accepts `{ email, passwordLength }` and the default sink is a no-op, so `no-console` stays an error with zero disables and a raw password cannot reach a logger even when a real sink is injected.

Forms delegate to a shared `useAuthSubmit` hook owning submit/success/error state; it persists a `session-<timestamp>` placeholder (documented dev stand-in, not a secret) and the storage key is a namespace, not a credential. Validation, Spanish copy, and the cross-field match error on `confirmPassword` match the spec.

Security posture for a web module: inputs validated via zod, no raw password logged, non-leaky catch-all error messages, no hardcoded secrets. The one real exposure — `localStorage` is readable by any same-origin script, so an XSS defeats token confidentiality — is documented at the top of `webTokenStorage.ts` and contrasted with the native keystore path; the future API wiring must keep it in mind.

Design fidelity is exact: every color, radius, font, and interaction directive maps to a centralized Tailwind token (`cream #f4f1ea`, `sage #8a9a5b`, `pink #e8c4c4`, `ink #3e4a3d`, `muted #6b705c`, `card rgba(255,255,255,0.88)`, 16px radius, Montserrat/Playfair, `focus:border` sage, `hover:-translate-y-0.5`, `transition-transform duration-150`, `backdrop-blur`). No invented colors.

### Platform-adaptive storage and why the native branch is real

`createTokenStorage()` returns `nativeTokenStorage` when `navigator.product === 'ReactNative'` (or when there is no `window`, a defensive fallback), otherwise `webTokenStorage`. Both satisfy the same three-method async interface, so `useAuthSubmit` depends only on the abstraction.

The native impl is not a stub. It performs the keystore calls through a lazily loaded module:

```ts
const SECURE_STORE_MODULE = 'expo-secure-store';
async function loadSecureStore(): Promise<ExpoSecureStore> {
  const mod = (await import(/* @vite-ignore */ SECURE_STORE_MODULE)) as ExpoSecureStore;
  return mod;
}
```

Computing the specifier at runtime plus `@vite-ignore` is what lets the web build stay green without `expo-secure-store` installed — confirmed by a clean `vite build` on this branch. The native test suite proves the three operations call `setItemAsync`/`getItemAsync`/`deleteItemAsync` under the shared key and that every store rejection maps to a Spanish, non-leaky error. The honest gap is that this runs against a mocked virtual module, never a device keystore; that verification has to happen when the Expo app consumes the interface.

### Redaction seam keeps `no-console` green and the password uncatchable

The user asked for a `console.log` of validated data; steering makes `no-console` an error. The resolution routes the intent through types rather than a disable:

```ts
export type AuthLogger = (label: string, redacted: RedactedCredentials) => void;
export function redactCredentials(values: Credentials): RedactedCredentials {
  return { email: values.email, passwordLength: values.password.length };
}
export const noopAuthLogger: AuthLogger = () => {};
```

Because the logger signature only accepts `RedactedCredentials`, a raw password cannot be handed to a sink through the normal path — the enforcement is structural, not conventional. The default is a no-op, so no `console.*` ships (grep across non-test auth sources: zero `console.`, zero `eslint-disable`). The form tests go further and serialize `logger.mock.calls`, asserting the literal password string never appears. This honestly satisfies the user's "log the validated data" intent while respecting the hard lint rule.

### Submit flow and the placeholder token

`useAuthSubmit` centralizes the behaviour: clear prior error, run `onSubmit ?? defaultSubmit`, set `submitted`, fire `onSuccess`; on throw, surface a fixed friendly message and swallow the detail so storage internals never leak into the UI. The default path logs the redacted shape then persists `session-${Date.now()}`:

```ts
await storage.saveToken(`session-${Date.now()}`);
```

The inline comment marks this as a dev placeholder, not a secret, and the test asserts the token matches `/^session-\d+$/` and does not contain the password. When a real `onSubmit` is injected, the default logger/token path is bypassed entirely (verified by the Registro test where an injected handler means the logger is never called) — the seam is correctly ready for the API/Supabase swap.

### Validation and Spanish copy

`loginSchema` enforces a non-empty valid email and an 8-char-min password; `registerSchema` extends it with `confirmPassword` and a `.refine` that attaches `'Las contraseñas no coinciden.'` to the `confirmPassword` path, so react-hook-form renders it under that input (test asserts the error's `id` is `register-confirm-password-error`). Empty-string defaults keep inputs controlled. All messages are Spanish and frozen in `copy.es.ts`. The schema and form suites cover invalid email, short password, mismatch, empty-confirm, and the valid happy path.

### localStorage XSS trade-off

`webTokenStorage.ts` opens with an explicit note that `localStorage` is readable by any same-origin script, so a successful XSS can exfiltrate the token, and names the hardened native keystore as the counterpart. The future API-wiring step should weigh httpOnly-cookie or in-memory token handling against this; for the web fallback with no OS keystore, `localStorage` is the pragmatic choice but the exposure remains.
